## 1. Contexto

O nível avançado exige uma **entrega reproduzível**: qualquer pessoa deve conseguir instalar, configurar, testar e executar o projeto em outro ambiente sem ajustes manuais e sem expor dados sensíveis. O PRD da etapa define cinco requisitos e quatro competências:

| ID | Requisito / competência |
|---|---|
| R1 | Configuração do LLM externa ao núcleo |
| R2 | Logs que ajudem a entender a execução, sem dados sensíveis |
| R3 | Versão do Python e bibliotecas documentadas |
| R4 | Pelo menos um teste da lógica local sem chamada real ao LLM |
| R5 | Validação em ambiente limpo, com registro |
| C01–C04 | Código organizado para terceiros, histórico do Git como evidência, falhas sem expor dados e execução em outro ambiente |

Antes de mudar qualquer código, foi feita uma **auditoria somente leitura** (commit de referência `65f1427`). O resultado foi **Pendente: 0 de 5 requisitos atendidos** (3 parciais e 2 ausentes). Os principais achados:

- **A aplicação não iniciava em ambiente limpo.** `src/llm.py` importava `google.api_core`, que não estava no `requirements.txt` nem vem com o `google-genai`. Só funcionava no `.venv` local por causa de pacotes antigos que sobraram ali.
- **O tratamento de erros não disparava.** O `google-genai` lança `google.genai.errors`, não as exceções do `api_core`. Os erros caíam em "erro inesperado" e mostravam ao usuário a mensagem crua da API.
- `temperature`, `max_output_tokens` e o prompt de sistema estavam fixos no código, e não havia `top_p` nem timeout.
- Não havia `logging`, testes com asserções, `README`/guia com o passo de clonar nem registro de validação.
- A versão do Python documentada (3.10+) não batia com o `.venv` (3.9.6).

Este ADR registra as decisões tomadas para resolver esses pontos.

## 2. Decisões

### 2.1 Auditoria antes da implementação, com rastreabilidade

O trabalho seguiu três passos: **auditar** (somente leitura, sem chamar o LLM, com segredos mascarados), **planejar** (uma task por pendência do relatório, com tabela de rastreabilidade) e **reauditar** depois das mudanças. As fases foram ordenadas por prioridade: primeiro o que **quebra** em ambiente limpo, depois o que **falta** e, por último, a **validação final**. Cada fase virou um commit com o requisito no título, por exemplo "(R1, R3, C03)", o que reforça a C02.

### 2.2 Tratamento de erros com as exceções do próprio SDK (R3, C03)

`src/llm.py` deixou de importar `google.api_core` e passou a capturar só o que o `google-genai` e o `httpx` realmente lançam:

| Exceção | Situação | Mensagem ao usuário |
|---|---|---|
| `errors.ClientError` 401/403, ou 400 com `API_KEY_INVALID` | Chave inválida | "Chave de API inválida ou sem permissão. Verifique o GEMINI_API_KEY no .env." |
| `errors.ClientError` 429 | Limite de uso | "Limite de uso da API atingido…" |
| `errors.ClientError` 404 | Modelo inexistente | "Modelo não encontrado. Verifique o GEMINI_MODEL no .env." |
| Outros `ClientError` | Solicitação recusada | Só o código HTTP, sem o texto da API |
| `errors.ServerError` | 5xx / instabilidade | "Serviço do LLM indisponível no momento…" |
| `errors.APIError` | Demais erros da API | Mensagem genérica |
| `httpx.TimeoutException` | Sem resposta no prazo | Mostra o timeout e sugere aumentar `LLM_TIMEOUT_SEGUNDOS` |
| `httpx.TransportError` | Sem rede | "Sem conexão com a API…" |
| `resposta.text` vazio ou `None` | Resposta vazia | "O modelo não retornou conteúdo…" |

Regras adotadas:

- Toda conversão usa `raise LLMError(...) from None`, para descartar a exceção original e não vazar URL, headers ou chave.
- O timeout é configurado no cliente com `types.HttpOptions(timeout=...)`.
- O caso **400 `API_KEY_INVALID`** foi descoberto na validação em ambiente limpo, porque o Gemini não responde 401 para chave inválida. Foi corrigido no commit `594d177`, com teste.
- Em `src/erros.py`, um erro **não previsto** mostra só o **tipo** da exceção. O stack trace completo só aparece com `EXTRATOR_DEBUG=1`. Erros previstos saem com código `1`, erros inesperados com `2` e o cancelamento pelo usuário (Ctrl+C) com `130`.

### 2.3 Todos os parâmetros do LLM no `.env`, com padrões e validação (R1)

`src/config.py` passou a ser o único lugar que lê o ambiente:

| Variável | Padrão | Validação |
|---|---|---|
| `GEMINI_API_KEY` | — (obrigatória) | não vazia |
| `GEMINI_MODEL` | `gemini-2.0-flash` | — |
| `LLM_TEMPERATURE` | `0` | float entre 0 e 2 |
| `LLM_TOP_P` | `1.0` | float entre 0 e 1 |
| `LLM_MAX_TOKENS` | `1024` | inteiro > 0 |
| `LLM_TIMEOUT_SEGUNDOS` | `30` | inteiro > 0 |
| `LLM_SYSTEM_PROMPT_ARQUIVO` | vazio (usa o prompt embutido) | arquivo legível, em UTF-8 e não vazio |

- Variável ausente ou vazia usa o padrão. Valor inválido gera `ConfigError` com mensagem clara, por exemplo "LLM_TEMPERATURE deve ser um número entre 0 e 2 (recebido: 'abc')".
- `chamar_llm` recebe o dicionário de configuração; `llm.py` não tem mais nenhum valor fixo.
- **O prompt de sistema pode ser trocado sem editar código.** Se `LLM_SYSTEM_PROMPT_ARQUIVO` apontar para um `.txt`, `montar_prompt` usa esse conteúdo; senão, usa o `SYSTEM_PROMPT` de `src/prompt.py`. A delimitação das anotações com `<anotacoes>` continua no user prompt em qualquer caso.
- O `.env.example` documenta todas as variáveis, com um comentário por linha e sem valores reais.

### 2.4 Logs seguros com `logging`, registrando só metadados (R2)

- **Novo módulo `src/registro.py`** com `configurar_logs()`. O nível vem de `LOG_LEVEL` (padrão `INFO`), a saída vai para `stderr` e pode ir também para um arquivo indicado em `LOG_ARQUIVO`. O formato é `%(asctime)s %(levelname)s %(name)s: %(message)s`.
- **O que é registrado:**
  - início e fim da execução, com código de saída e duração total;
  - configuração carregada, via `resumo_seguro()`: modelo, temperatura, top_p, max_tokens, timeout e a origem do prompt (embutido ou arquivo);
  - tamanho da entrada em caracteres;
  - envio da solicitação ao LLM;
  - duração da chamada e tamanho da resposta;
  - tipo do erro, quando houver.
- **O que nunca é registrado:** chave de API, headers, texto das anotações e resposta integral.
- **Os loggers de `httpx`, `httpcore`, `google_genai` e `urllib3` ficam em `WARNING`**, porque em `DEBUG` eles podem registrar URLs e headers.
- **`print` é usado só para o que é do usuário**: a lista de tarefas e a pergunta de salvar. Os logs vão para `stderr`, então não se misturam com a saída.
- `*.log` e `logs/` foram adicionados ao `.gitignore`.

### 2.5 Dependências com faixas de versão e Python fixado (R3)

- `requirements.txt`: `google-genai>=1.47,<2`, `httpx>=0.28,<1` e `python-dotenv>=1.0,<2`. O `httpx` foi declarado porque é importado diretamente em `llm.py`.
- **Novo `requirements-dev.txt`** com `-r requirements.txt` e `pytest>=8,<9`, separando o que é de execução do que é de desenvolvimento.
- **Novo `.python-version`** com `3.10`.
- A conferência entre imports e dependências declaradas não encontrou nenhuma biblioteca externa faltando ou sobrando.

### 2.6 Testes automatizados com `pytest`, sem chave e sem rede (R4)

- `tests/conftest.py` adiciona `src/` ao `sys.path`. Uma fixture `autouse` remove todas as variáveis do projeto do ambiente e troca `load_dotenv` por uma função vazia, para que **nenhum teste leia o `.env` real**.
- O SDK é simulado com `unittest.mock.patch("llm.genai.Client")`. O ambiente é controlado com `monkeypatch`.
- São 66 testes (parametrizados), organizados assim:

| Arquivo | Cobre |
|---|---|
| `test_entrada.py` | entrada vazia ou só com espaços, limite de 20.000 caracteres (no limite e acima), arquivo inexistente, pasta no lugar de arquivo, arquivo em Latin-1 |
| `test_prompt.py` | data de referência em `DD/MM/AAAA`, anotações delimitadas, prompt de sistema alternativo |
| `test_config.py` | falta de chave, valores padrão, valores inválidos, ausência da chave no `resumo_seguro` |
| `test_llm.py` | resposta simulada, resposta vazia, `ClientError` 400/401/429, `ServerError`, timeout, ausência da chave na mensagem e nos logs |
| `test_casos.py` | fluxo completo de cada arquivo em `tests/casos/`, comparado com o status esperado (OK ou ERRO) |

O script `tests/rodar_casos_local.py` foi mantido como ferramenta exploratória. A verificação com asserções passou a ser feita por `test_casos.py`.

### 2.7 Guia de execução único e validação em ambiente limpo registrada (R5, C01, C04)

- **O `GuiaDeExecucao.md` foi mantido como documento principal**, em vez de criar um `README.md` separado, para não haver duas fontes. Ele cobre clonar, criar o venv (macOS/Linux e Windows), instalar, configurar cada variável, executar (arquivo, stdin e `--texto`), logs, testes, bibliotecas e estrutura de pastas.
- **Todos os módulos de `src/` ganharam docstrings.**
- **A validação foi feita num clone novo**, fora do projeto, com venv novo e instalação só pelo `requirements-dev.txt`. Ela foi registrada em `VALIDACAO.md` com sistema operacional, versão do Python, comandos, resultados por cenário e três problemas encontrados, cada um com o que aconteceu e a correção: `google.api_core` ausente, o 400 `API_KEY_INVALID` e um 503 transitório.

## 3. Alternativas consideradas

| Alternativa | Por que não foi escolhida |
|---|---|
| **Declarar `google-api-core` no `requirements.txt`** | Faria a aplicação iniciar, mas os `except` continuariam sem disparar, porque o `google-genai` não lança essas exceções. Usar `google.genai.errors` resolve R3 e C03 de uma vez e remove uma dependência. |
| **`config.yaml` / `config.json` em vez de `.env`** | O projeto já usava `.env` + `python-dotenv` desde o básico. Um segundo mecanismo dividiria a configuração em dois lugares sem ganho real para poucos parâmetros escalares. |
| **Prompt de sistema direto numa variável de ambiente** | Prompts têm várias linhas e são difíceis de escrever no `.env`. Apontar para um arquivo `.txt` é mais legível e versionável. |
| **Registrar o prompt e a resposta em `DEBUG`** | Ajudaria a depurar, mas criaria o risco de gravar dados pessoais das anotações em arquivos de log. Optou-se por registrar só tamanhos e durações. |
| **`print` para os logs** | Não permite controlar nível nem destino e mistura diagnóstico com a saída do usuário. |
| **Testes contra a API real** | Dependem de chave, rede e cota, não são determinísticos e podem vazar a chave em CI. O PRD exige testes sem chamada real. |
| **Versões exatas (`==`) no `requirements.txt`** | Mais reproduzível, mas impede correções de segurança e conflita mais fácil com outros ambientes. Faixas com limite superior na próxima versão maior equilibram estabilidade e manutenção. |
| **`pyproject.toml` com empacotamento** | Excede o escopo de uma CLI executada como script. `requirements*.txt` + `.python-version` atendem ao R3 com menos estrutura. |
| **Retry automático em 429/5xx** | Não é exigido pelo PRD. O 503 visto na validação foi tratado com mensagem clara, e o usuário pode repetir a execução. Fica como evolução possível. |

## 4. Consequências

### Positivas

- **A reauditoria aprovou com ressalvas:** 5 de 5 requisitos e 4 de 4 competências atendidos.
- **A aplicação instala e roda em ambiente limpo** só com o que está declarado nas dependências.
- **Modelo, amostragem, limites, timeout e prompt mudam sem tocar no código.** Um valor inválido é detectado na inicialização, com mensagem clara.
- **Toda falha conhecida da API tem mensagem amigável**, sem stack trace, texto cru da API ou chave.
- **Os logs permitem entender e cronometrar uma execução** sem expor segredos ou conteúdo, e os testes verificam isso.
- **A suíte `pytest` roda sem chave e sem internet**, então pode entrar num CI sem configurar segredos.
- **Cada mudança se liga a uma pendência do relatório e a um commit**, o que torna o histórico uma evidência do processo.

### Negativas e riscos aceitos

- **Mais superfície de configuração:** mais variáveis para documentar e validar. Mitigado pelos padrões seguros e pelo `.env.example` comentado.
- **Logs sem conteúdo dificultam depurar respostas ruins do modelo.** Para analisar a qualidade da extração, é preciso rodar o caso manualmente.
- **Os mocks dependem da API interna do SDK** (`genai.Client`, `errors.ClientError(code, response_json)`). Uma versão maior nova do `google-genai` pode quebrar os testes. O limite `<2` reduz esse risco.
- **A saída continua em texto livre** com formato pedido no prompt, sem validação estrutural (JSON + schema). A qualidade da extração não é medida por métrica automática.
- **Sem retry:** instabilidades do serviço (503) exigem que o usuário rode de novo.
