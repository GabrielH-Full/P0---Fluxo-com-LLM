# ADR 001: Arquitetura do nível básico do extrator de tarefas (CLI em Python + Gemini)

**Status:** Aceito (implementado no nível básico; evoluído depois no intermediário e no avançado)
**Data:** 12/11/2026
**Bloco:** P0 - Fluxo com LLM, etapa 1 de 3 (nível básico)
**Documentos de origem:** [PRD](../p0-basico/PRD.md) · [TechSpec](../p0-basico/TECHSPEC.md) · [Tasks](../p0-basico/TASKS.md)
**Implementação de referência:** commit `5864eca`, integrado na `main` pelo PR #1 (`4e0cb9e`)

## 1. Contexto

Depois de reuniões, as anotações costumam ser apressadas: frases soltas, nomes abreviados, datas relativas ("sexta", "amanhã") e decisões misturadas com conversa. O objetivo do nível básico é entregar um fluxo mínimo, funcional e reproduzível de ponta a ponta:

```
entrada pelo terminal → solicitação ao LLM → resposta apresentada ao usuário
```

A entrada é linguagem livre, sem padrão fixo, e exige interpretar ambiguidades, separar tarefa de decisão e resolver datas relativas. Regex e regras fixas não dão conta disso, por isso a solução usa um LLM.

Restrições desta etapa (PRD §6, §7 e §10):

- Python (RF01), entrada pelo terminal (RF02) e saída no terminal (RF04).
- Credenciais fora do código, em `.env` não versionado (RNF01, RNF02).
- Reproduzível por terceiros com `requirements.txt` e README (RNF03, RNF04).
- Código em funções pequenas, pronto para evoluir (RNF05).
- Fora do escopo: JSON validado, retry, chunking, defesa contra prompt injection, testes automatizados, banco de dados, interface gráfica e web.

## 2. Decisão

### 2.1 Aplicação de linha de comando com fluxo linear

Um script Python executado com `python src/main.py`, sem servidor nem interface gráfica. O fluxo é sequencial:

```
obter_config → ler_entrada → validar_entrada → montar_prompt → chamar_llm → print
```

### 2.2 Separação em módulos por responsabilidade

| Módulo | Responsabilidade | Exceção própria |
|---|---|---|
| `src/config.py` | Carrega o `.env` com `python-dotenv` e devolve chave e modelo | `ConfigError` |
| `src/entrada.py` | Lê o texto (arquivo `.txt` em UTF-8 ou `stdin`) e valida (vazio, limite de 20.000 caracteres) | `EntradaInvalidaError` |
| `src/prompt.py` | Monta o par `(system, user)` | — |
| `src/llm.py` | Cria o cliente, chama o modelo e devolve o texto | `LLMError` |
| `src/main.py` | CLI com `argparse`, orquestração e tratamento de erros | — |

Cada módulo tem uma única razão para mudar. A troca de provedor, por exemplo, fica restrita a `llm.py` e `config.py`.

### 2.3 Provedor e modelo: Google Gemini via SDK oficial `google-genai`

- Cliente: `genai.Client(api_key=...)` e `client.models.generate_content(...)`.
- Modelo configurável por `GEMINI_MODEL` no `.env` (padrão `gemini-2.0-flash`), para não fixá-lo no código.
- `temperature=0` e `max_output_tokens=1024`, para respostas mais estáveis numa tarefa de extração.

### 2.4 Credenciais em variáveis de ambiente

- `GEMINI_API_KEY` e `GEMINI_MODEL` são lidos do `.env` com `load_dotenv()`.
- O `.env` está no `.gitignore`. Só o `.env.example`, sem segredos, é versionado.
- Sem chave, a aplicação para com `ConfigError` e a mensagem "Defina GEMINI_API_KEY no arquivo .env (veja o .env.example)."

### 2.5 Engenharia de prompt: system prompt fixo e anotações delimitadas

- **System prompt** com papel, regras e formato de saída fixo:
  - extrair só tarefas concretas; decisões e conversa não são tarefas;
  - converter datas relativas usando a data de referência;
  - escrever `não informado` quando responsável ou prazo não estiverem claros, sem inventar (RF05);
  - uma tarefa por linha: `N. Responsável: X | Ação: Y | Prazo: DD/MM/AAAA`;
  - responder `Nenhuma tarefa identificada.` quando não houver tarefas;
  - responder em português do Brasil, sem texto além da lista.
- **User prompt** com a data de referência e as anotações entre `<anotacoes>...</anotacoes>`. Os delimitadores já preparam a defesa contra prompt injection do nível avançado.

### 2.6 Data de referência explícita (`--data`)

A data da reunião é passada com `--data DD/MM/AAAA` (padrão: hoje) e validada no `argparse` com `strptime`. Assim o modelo consegue resolver "sexta" e "amanhã" de forma determinística em relação à reunião, e não ao dia em que o script roda.

### 2.7 Saída em texto simples

O resultado é o texto do modelo impresso no terminal, sem parsing. A saída em JSON com schema validado fica para o nível intermediário.

### 2.8 Tratamento de erros sem stack trace

`main.py` captura `ConfigError`, `EntradaInvalidaError` e `LLMError`, imprime `Erro: <mensagem>` em `stderr` e sai com código `1`. Os erros do SDK são convertidos em `LLMError` com mensagem amigável (chave inválida, limite de uso, sem conexão), sem expor a chave.

### 2.9 Dependências mínimas

`requirements.txt` com `google-genai>=1.0.0` e `python-dotenv>=1.0.0`. CLI e leitura de entrada usam só a biblioteca padrão (`argparse`, `sys`, `datetime`).

## 3. Alternativas consideradas

| Alternativa | Por que não foi escolhida |
|---|---|
| **Anthropic (Claude) via SDK `anthropic`** | Era a opção original do TechSpec (§4.1, §4.4 e §6 ainda citam `ANTHROPIC_API_KEY` e `messages.create`). Foi trocada pelo Gemini por conta do SDK simples e da boa qualidade de extração em português. Como o provedor está isolado em `llm.py`, a troca não afetou o resto. |
| **Regex / regras fixas** | Não lidam com linguagem livre, ambiguidade ("ana talvez") nem datas relativas (PRD §4). |
| **Saída em JSON já no básico** | Exige schema, validação e retry, que são escopo do intermediário. Texto com formato fixo basta para a métrica de sucesso do básico. |
| **Script único (`app.py`)** | Existiu num rascunho anterior e foi removido no commit `5864eca`. Um arquivo só dificultaria evoluir prompt, cliente e validação de forma independente (RNF05). |
| **Interface web ou gráfica** | Fora do escopo (PRD §10). O terminal atende ao público e ao objetivo da etapa. |
| **Modelo fixo no código** | Dificulta trocar por custo ou qualidade e quebra se o modelo for descontinuado. Por isso foi para o `.env`. |
| **Resolver datas relativas no Python** | Seria preciso um parser de linguagem natural para datas. Passar a data de referência ao modelo é mais simples e suficiente para o básico. |

## 4. Consequências

### Positivas

- Fluxo de ponta a ponta funcional com pouco código (cerca de 180 linhas em `src/`).
- Módulos isolados, que permitiram ao intermediário e ao avançado acrescentar logs, parâmetros no `.env`, testes com `pytest` e tratamento de erros mais robusto sem reescrever a arquitetura.
- Nenhum segredo no código. Modelo e chave trocam pelo `.env`.
- Erros previsíveis aparecem como mensagens claras, sem stack trace.
- Os delimitadores `<anotacoes>` já servem de base para a defesa contra prompt injection.

### Negativas e riscos aceitos

- **Saída não estruturada:** o formato depende de o modelo seguir o system prompt. Mitigado por `temperature=0` e formato fixo; a solução definitiva (JSON validado) foi deixada para o intermediário.
- **Verificação só manual:** os cenários V1 a V7 do TechSpec §9 foram executados à mão. Testes automatizados ficaram para os níveis seguintes.
- **Parâmetros fixos no código:** `temperature` e `max_output_tokens` ficaram em `llm.py`. Foram levados para o `.env` no intermediário (commit `06bf96f`).
- **Captura de erros incompatível com o SDK:** `llm.py` capturava exceções de `google.api_core.exceptions` (`Unauthenticated`, `ResourceExhausted` etc.), mas o `google-genai` levanta `google.genai.errors` (`ClientError`, `ServerError`, `APIError`). Na prática, alguns erros da API podiam escapar sem mensagem amigável. Corrigido no commit `06bf96f`; o caso de chave inválida devolvida como `400 API_KEY_INVALID` foi tratado no `594d177`.
- **Dependências com versão mínima aberta** (`>=`): risco de quebra com versões futuras. As faixas foram fixadas no commit `c5b5077`.
- **Limite de 20.000 caracteres** em vez de chunking: entradas maiores são recusadas com erro claro.

## 5. Desvios em relação ao TechSpec

O que foi implementado diferente ou além do previsto:

| Item | TechSpec | Implementação |
|---|---|---|
| Provedor | Texto misto entre Anthropic (§4.1, §4.4, §6) e Gemini (§2, §7) | Gemini (`google-genai`) em todo o código e no `.env.example` |
| Entrada | `--arquivo` e `stdin` | Também `--texto/-t`, para passar as anotações direto como argumento (atende RF02 "via argumento") |
| Saída | Só `print` | Depois do `print`, pergunta via `/dev/tty` se deve salvar a lista em `tarefas_DD-MM-AAAA.txt` |
| Arquivo de exemplo | `exemplo.txt` na raiz ou em `tests/casos/` | `tests/casos/exemplo.txt` |
